# מחולל דוחות מעבדה (Lab Report Generator)

אפליקציית Windows מקומית ליצירת דוחות מעבדה הנדסית בעברית (Word `.docx`),
בהתאם למבנה, לניסוח ולעימוד של דוחות "המעבדה ההנדסית המרכזית בע"מ" (מקבוצת
המכון לחקר הכשל). המשתמש מזין פרטי דוח קצרים, כותב בעצמו את טקסט הדוח (כללי/
ממצאים/דיון ומסקנות) ומצרף תמונות; המערכת בונה את קובץ ה-Word הסופי מתוך
התבנית הרשמית, כולל נספח תמונות נפרד וספירת עמודים מדויקת.

## מבנה הפרויקט

| קובץ/תיקייה | תפקיד |
|---|---|
| `app.py` | ממשק המשתמש (Flet), בעברית ו-RTL מלא. |
| `report_builder.py` | בניית ה-`.docx` הסופי מהתבנית (docxtpl + python-docx), כולל נספח התמונות וספירת העמודים. |
| `ai_service.py` | שכבת AI עצמאית מספק ליצירת כיתובי תמונות (vision) בלבד - אינה נוגעת בטקסט הדוח. |
| `approved_reference_service.py` | שכבת "דוגמאות מאושרות" - במצב פיתוח סורקת את `data/reference_examples/` בזמן קריאה; בגרסה ארוזה (frozen) קוראת את `data/approved_reference_pack/` הנגזר בלבד. ראו "שכבת דוגמאות מאושרות" למטה. |
| `reference_review_service.py` | לוגיקת מסך "בדיקת דוחות ייחוס" (כלי בדיקה/תיוג מקומי, **פיתוח בלבד** - לא נטען ולא מוצג בגרסה ארוזה). |
| `build_approved_reference_pack.py` | סקריפט build שבונה מחדש את `data/approved_reference_pack/` הנגזר מתוך הדאטהסט החי - יש להריץ לפני כל ארוז לגרסת Windows. |
| `word_page_counter.py` | אוטומציית COM של Microsoft Word לחישוב מספר עמודים אמיתי (דורש Word מותקן). |
| `photo_service.py` | אימות/שינוי גודל/תצוגה מקדימה/חיתוך תמונות. |
| `template_prep.py` | "קומפילציה" חד-פעמית של התבנית הריקה לגרסה עם תגי Jinja - **אף פעם לא נוגע בקובץ המקורי**; התוצר נשמר תחת `build/templates/`. |
| `config.py` | נתיבים והגדרות (נטענות גם מקובץ `.env`), כולל דגלי פיתוח/ייצור (`FROZEN`, `REFERENCE_REVIEW_ENABLED`, `USE_APPROVED_REFERENCE_PACK`). |
| `prompts/caption_prompt.txt` | הנחיות הכתיבה שנשלחות ל-AI ליצירת כיתובי תמונות. |
| `data/style_guide.md` | מדריך סגנון שחולץ מהדוחות לדוגמה - רפרנס לכותב האנושי ולכיתובי ה-AI. |
| `data/reference_examples/` | דאטהסט הבדיקה/תיוג הגולמי (PDF, תמונות מקור, `captions.he.json`) - **פיתוח בלבד**, אף פעם לא נארז לגרסת הייצור. |
| `data/approved_reference_pack/` | **תוצר נגזר** (נבנה על ידי `build_approved_reference_pack.py`) - רק בלוקים מאושרים, תצוגות מקדימות קטנות, ללא PDF/תמונות מקור/נתיבים מקומיים. זה מה שנארז לגרסת הייצור. |
| `templates/` | **קבצי המקור המקוריים בלבד** - התבנית הריקה ודוחות לדוגמה. לא נכתב ולא ישונה קובץ בתיקייה זו על ידי האפליקציה. רק `empty_report_template.docx` נארז לגרסת הייצור (ראו "הפצה לייצור" למטה) - `*_refernces/`/`*_references/` הן דוחות לקוח מקוריים, פיתוח בלבד. |
| `tests/` | בדיקות יחידה (pytest). |

## התקנה

1. Python 3.12 ומעלה.
2. סביבה וירטואלית (מומלץ):
   ```bash
   python -m venv .venv
   .venv\Scripts\activate
   ```
3. התקנת חבילות:
   ```bash
   pip install -r requirements.txt
   ```
4. **Microsoft Word** מותקן על המחשב - נדרש לספירת עמודים אמיתית (ראו "מגבלות
   ידועות" למטה). ללא Word, הדוח עדיין נוצר, עם "-" במקום מספרי העמודים.
5. יצירת קובץ הגדרות אישי:
   ```bash
   copy .env.example .env
   ```
   ולאחר מכן למלא ב-`.env` את `AI_API_KEY` (ואת `AI_PROVIDER`, אם רוצים
   ספק אחר מ-`anthropic`). המודל חייב לתמוך בקלט תמונות (vision) - הוא
   משמש רק ליצירת כיתובי תמונות. **אין להעלות את `.env` ל-Git.**

## הרצה

```bash
python app.py
```

בהרצה הראשונה תיבנה אוטומטית (חד-פעמית) גרסת עבודה של התבנית עם תגי Jinja,
תחת `build/templates/` - הקובץ המקורי ב-`templates/` לעולם לא נכתב.

## זרימת העבודה

1. מילוי פרטי הדוח (מספר בדיקה, תאריך, לקוח, נושא וכו').
2. כתיבת טקסט הדוח בעצמו - "כללי", "ממצאים" ו"דיון ומסקנות" - בשדות
   הייעודיים. הטקסט הזה הוא הטקסט הרשמי של הדוח; המערכת אינה עורכת,
   מרחיבה או מנסחת אותו מחדש בשום שלב.
3. העלאת תמונות. לכל תמונה: תצוגה מקדימה, כפתור "חיתוך" אופציונלי (חיתוך
   מרווחים מהקצוות עם תצוגה חיה), וכיתוב עברי הנוצר אוטומטית על ידי מודל AI
   התומך בראייה, לפי מה שנראה בתמונה בפועל בלבד - ניתן לערוך או למחוק
   כיתוב כזה בכל שלב; ברגע שהמשתמש עורך כיתוב ידנית, הוא לעולם לא נדרס
   שוב (גם אם התמונה נחתכת מחדש).
4. סידור התמונות בגרירה לסדר הרצוי בנספח.
5. לחיצה על "צור דוח Word": נבנה קובץ הדוח עם טקסט הדוח בלבד בגוף הראשי,
   אחריו מעבר עמוד מאולץ ונספח תמונות נפרד (תמונה + כיתוב לכל תמונה, לפי
   הסדר שנבחר). מספר העמודים הכולל ומספר עמודי נספח התמונות מחושבים
   באופן אוטומטי ומוזנים לתבנית (ראו "מגבלות ידועות"). הקובץ נשמר בשם
   `<מספר הבדיקה>pub.docx` בתיקיית `reports/`, ותיקיית הפלט נפתחת אוטומטית.

## הפרדה בין ספק ה-AI לפורמט Word

ה-AI **אף פעם** לא נוגע בטקסט הדוח (כללי/ממצאים/דיון ומסקנות) ולעולם לא
מתבקש לייצר עיצוב Word. השימוש היחיד ב-AI בכל המערכת הוא יצירת כיתוב קצר
לכל תמונה בנפרד, המוגבל לתיאור תוכן חזותי גנרי בלבד - לעולם לא ממצא, נזק,
מדידה או מסקנה. כל הפורמט (RTL, יישור, גופנים, כותרות) מגיע מהתבנית
המקורית עצמה: `report_builder.py` רק מכניס טקסט/תמונות לתוך מבנה שכבר
קיים בתבנית.

## שכבת דוגמאות מאושרות (approved_reference_service.py)

כדי שכיתובי ה-AI ילמדו בהדרגה את המינוח והסגנון של המעבדה, `ai_service.py`
יכול לצרף לבקשת הכיתוב הקשר מבוסס דוגמאות **מאושרות בלבד**. יש שני מקורות
נתונים, לפי `config.USE_APPROVED_REFERENCE_PACK` (`True` בגרסה ארוזה):

- **פיתוח** (`python app.py` רגיל): סריקה **דינמית לחלוטין** של
  `data/reference_examples/` בזמן קריאה - אין אינדקס סטטי שיכול
  "להתיישן"; בלוק שאושר הרגע במסך "בדיקת דוחות ייחוס" זמין לבקשה הבאה
  מיד, ללא בנייה מחדש.
- **ייצור (frozen)**: קריאה מ-`data/approved_reference_pack/` - התוצר
  הנגזר, הקטן והמסונן שנבנה מראש על ידי `build_approved_reference_pack.py`
  (ראו "הפצה לייצור" למטה). גרסת הייצור **אינה** נוגעת בדאטהסט הגולמי
  כלל - הוא אפילו לא נארז יחד איתה.

בשני המצבים:

- **רק בלוקים מאושרים**: `status: "approved"`, טקסט לא ריק, ולפחות תמונה
  אחת. בלוקים "טרם נבדק"/"דרושה עריכה"/"לא ניתן לקבוע" - וכל בלוק פגום -
  מדולגים תמיד.
- **בלוק רב-תמונות אינו תווית מדויקת**: בלוק שבו כמה תמונות חולקות כיתוב
  קבוצתי אחד מסומן במפורש כ"הקשר סגנוני בלבד" ומעולם אינו הופך לדוגמה
  חזותית (תמונה בפועל) - רק בלוקים עם תמונה בודדת יכולים לשמש כדוגמה
  חזותית.
- **גבול קבוע על גודל/עלות**: מספר הדוגמאות, גודל הקטע הטקסטואלי, וגודל
  כל תצוגה חזותית מוגבלים (`APPROVED_REFERENCE_MAX_EXAMPLES`,
  `APPROVED_REFERENCE_MAX_CONTEXT_CHARS`,
  `APPROVED_REFERENCE_PREVIEW_MAX_DIMENSION_PX` ב-`.env`) - כך שהעלות/גודל
  הבקשה ל-AI נשארים קבועים גם כשמאגר הדוגמאות המאושרות גדל עם הזמן.
- מסך "יצירת דוח" מציג הערה קצרה כשיש דוגמאות זמינות - ללא נתיבים, שמות
  קבצים או JSON גולמי (בייצור: משפט קבוע קצר; בפיתוח: כולל מספר הדוגמאות).

### מצב טקסט מול מצב חזותי (`APPROVED_REFERENCE_MODE`)

- `text` (ברירת מחדל) - רק קטע טקסט קצר בעברית מצורף להנחיות המערכת;
  לעולם לא נשלחות תמונות דוגמה ל-AI.
- `visual` - בנוסף, מספר מוגבל של בלוקים מאושרים **עם תמונה בודדת**
  נשלחים כדוגמאות אמיתיות (תמונה + הכיתוב המאושר שלה) יחד עם התמונה
  החדשה, **בבקשה אחת**. לבלוק עם חיתוך (crop) נשלחת תצוגת החיתוך המאושר
  בלבד - לעולם לא כל התמונה המקורית. בלוקים רב-תמונות עדיין יכולים לתרום
  כטקסט בלבד (לא כתמונה) אם נותר תקציב. ההנחיות למודל מבהירות במפורש
  שהדוגמאות משמשות לסגנון/מינוח בלבד ואינן ראיה לגבי התמונה החדשה - וכל
  חוקי הבטיחות הקיימים (איסור על ממצא/נזק/מדידה/מסקנה) נשארים בתוקף
  במלואם.
- `off` - זהה ל-`APPROVED_REFERENCES_ENABLED=0`.

ניתן לכבות את הפיצ'ר לגמרי עם `APPROVED_REFERENCES_ENABLED=0` ב-`.env`.

## הפצה לייצור (בניית גרסת Windows לאבא)

מסך "בדיקת דוחות ייחוס" והדאטהסט הגולמי (`data/reference_examples/`,
PDF, תמונות מקור באיכות מלאה) הם **כלי פיתוח/תיוג בלבד** ואסור שיגיעו
למחשב של אבא. שני מנגנונים נפרדים דואגים לכך:

1. **`config.REFERENCE_REVIEW_ENABLED`** - `True` כברירת מחדל בהרצת פיתוח
   רגילה, `False` כברירת מחדל בגרסה ארוזה (`sys.frozen`). כשהוא `False`,
   מסך הבדיקה כלל לא נבנה (לא רק מוסתר) - כך שהוא גם לא מנסה לקרוא
   דאטהסט שלא נארז. ניתן לעקוף לצורכי אבחון עם `REFERENCE_REVIEW_ENABLED=1`
   ב-`.env`.
2. **`ReportGenerator.spec`** - אורז רק את `data/approved_reference_pack/`
   הנגזר (ולא את `data/reference_examples/`), ורק את
   `templates/empty_report_template.docx` (ולא את תיקיות דוחות הלקוח
   המקוריים `templates/*_refernces/`).

### שלבי בנייה

```bash
# 1. לוודא שכל הבלוקים הרלוונטיים אושרו במסך "בדיקת דוחות ייחוס" (פיתוח).

# 2. לבנות מחדש את חבילת הדוגמאות המאושרות לייצור - תמיד לפני ארוז:
python build_approved_reference_pack.py

# 3. לארוז לגרסת Windows:
pyinstaller ReportGenerator.spec
```

הפלט נמצא תחת `dist/ReportGenerator/`.

### העברה למחשב של אבא

1. להעתיק את כל תיקיית `dist/ReportGenerator/` (לא רק את קובץ ה-`.exe`)
   למחשב היעד.
2. ליצור שם קובץ `.env` נפרד (מ-`.env.example`) עם `AI_API_KEY` אמיתי -
   **קובץ ה-`.env` אף פעם לא נארז בתוך ה-build ואסור להעתיק אותו מהמחשב
   שלך** - יש למלא אותו מחדש/בנפרד במחשב היעד, ולוודא שהוא יושב ליד
   `ReportGenerator.exe` (לא בתוך `_internal`).
3. לוודא ש-Microsoft Word מותקן במחשב היעד (לספירת עמודים אמיתית -
   אופציונלי, הדוח עדיין ייווצר בלעדיו).
4. להריץ את `ReportGenerator.exe`. מסך "בדיקת דוחות ייחוס" לא יופיע -
   רק מסך יצירת הדוח, עם הערת השקיפות הקצרה כשדוגמאות מאושרות פעילות.

## מגבלות ידועות והחלטות עיצוב

- **פריסת תמונות**: בדוחות המקוריים התמונות ממוקמות ידנית ב"ציור חופשי"
  (floating images) עם כיתובים מסכמים למספר תמונות יחד. docxtpl/python-docx
  אינם יכולים לשחזר זאת באופן אמין. הפתרון: נספח תמונות נפרד (אחרי מעבר
  עמוד מאולץ) עם טבלת תמונות (grid) שנבנית אוטומטית, כיתוב אחד לכל תמונה,
  ממוספר "תמונה N". כל שורה בטבלה מוגדרת כבלתי-ניתנת-לפיצול (`w:cantSplit`)
  כך שתמונה וכיתובה לעולם לא יתפצלו בין עמודים.
- **מספר עמודים**: נספר באופן מדויק (לא הערכה) באמצעות אוטומציית COM של
  Microsoft Word (`word_page_counter.py`) - פותחת עותק חבוי של Word, מודדת
  את העימוד האמיתי, וסוגרת אותו. דורש התקנת Word על המחשב המריץ את
  האפליקציה. אם Word אינו זמין או שהאוטומציה נכשלת, שדות אלה יוצגו כ-"-"
  והדוח עדיין ייווצר בהצלחה (ההודעה תוצג למשתמש).
- **מדריך הסגנון** (`data/style_guide.md`) נבנה מ-8 דוחות לדוגמה בלבד -
  פחות מ-15–25 המומלצים. מומלץ להוסיף עוד דוגמאות ולעדכן את המדריך.
- דוחות הדוגמה נמצאים בפועל תחת `templates/crane_refernces/`,
  `templates/chassis_references/` ו-`templates/actuator_refernces/`
  (ולא תחת `templates/reference_reports/`) - כך נשמרו קבצי המשתמש כפי
  שהם, ללא שינוי מבנה תיקיות.

## בדיקות

```bash
pytest
```

בודקות: בניית הדוח מהתבנית, כיוון RTL בטקסט ובכיתובי תמונות, נספח
התמונות (מעבר עמוד, `cantSplit`, סימנייה), עיבוד תמונות (אימות/שינוי
גודל/חיתוך), ואימות כיתובי ה-AI (סכימת pydantic, ניסיונות חוזרים, טיפול
בשגיאות, מצב חזותי - `tests/test_ai_service.py`). ספירת העמודים האמיתית
מושבתת בבדיקות (`PAGE_COUNT_AUTOMATION_ENABLED=False`
דרך `tests/conftest.py`) כדי שהחבילה תרוץ במהירות ובלי תלות ב-Word מותקן;
`tests/test_word_page_counter.py` בודק את לוגיקת אוטומציית ה-COM עם Word
מדומה (mock), ומכיל בדיקת אינטגרציה נפרדת עם Word אמיתי שמופעלת רק אם
מגדירים `RUN_WORD_INTEGRATION_TESTS=1`. אף בדיקה בחבילה אינה מבצעת קריאת
API אמיתית ל-Anthropic/OpenAI.

בדיקות ספציפיות להפצה לייצור:
- `tests/test_production_mode.py` - הסתרת/הצגת מסך הבדיקה לפי
  `config.REFERENCE_REVIEW_ENABLED`, ומיתוג מקור הנתונים (דאטהסט חי מול
  חבילה נגזרת) לפי `config.USE_APPROVED_REFERENCE_PACK`.
- `tests/test_build_approved_reference_pack.py` - רק בלוקים מאושרים עם
  תמונה שמישה נכללים; `cannot_determine`/תמונת מקור חסרה מוחרגים; תצוגת
  חיתוך משתמשת באזור החיתוך המאושר בפועל (לא בתמונה המלאה); בלוק
  רב-תמונות אינו מקבל תצוגה חזותית כלל; אף קובץ תמונה מקורי לא משתנה;
  הבנייה דטרמיניסטית (הרצה חוזרת מפיקה תוצאה זהה).

## הוספת ספק AI נוסף

`ai_service.py` בנוי סביב מחלקת בסיס מופשטת `AIService` עם שיטה מופשטת
יחידה, `generate_photo_caption`. כל הלוגיקה של ניסיונות חוזרים/טיימאאוט/
פענוח JSON משותפת ב-`_RetryingAIService`; הדבר היחיד שכל ספק חדש צריך
לממש הוא
`_call_model(system_prompt, user_message, image_bytes, media_type, reference_images)`
(הפרמטר האחרון - רשימת דוגמאות חזותיות מאושרות, ריקה כברירת מחדל, ריקה
תמיד כש-`APPROVED_REFERENCE_MODE` אינו `visual`). ה-V1 כולל שני מימושים
(`anthropic`, `openai`); ספק עתידי כמו Gemini (למשל
דרך `google-generativeai`) יידרש רק למחלקה חדשה היורשת מ-`_RetryingAIService`
עם `_call_model` משלה, ושורה אחת נוספת במילון `_PROVIDERS` - ללא שינוי
מבני נוסף בשום מקום אחר במערכת.
